Why CSA keeps two kinds of memory

Compressed Sparse Attention (CSA) is one of DeepSeek V4's attention mechanisms for long sequences. It keeps individual entries for recent tokens, builds compressed entries spanning the history, and selects which compressed entries a query will read.

Consider editing a call to a function whose definition appeared much earlier in a long file. The surrounding lines help determine how the call is being used; the distant definition may be needed to determine which arguments it accepts. Attention should have a way to consult both.

In the ordinary causal attention from Foundations, a query compares with a key for each permitted token position and combines the corresponding values. During generation, a layer saves its earlier keys and values in a key/value cache. Saving them avoids computing them again, but attention still has to store and read them. With their widths fixed, doubling the retained positions doubles their vector storage and the candidates for a query that reads the full history.

Recent detail and a longer reach

A short sliding window bounds those costs. It retains a separate entry for each recent token, so attention can distinguish nearby positions directly. But once the function definition leaves the window, its separate entry is no longer available. Making the window larger postpones the difficulty and increases the cost again.

We could instead replace the entire history with one average. That keeps very little memory, but makes all the distant definitions, calls and other passages contribute to the same vector. There is no longer a collection of separate places for a later query to choose among.

CSA keeps a smaller collection by summarizing groups of token positions. Each compressed entry combines several positions, while separate entries cover different parts of the history. A query can consult those summaries when the relevant passage lies beyond the recent window. Compression can lose information, so CSA also retains the individual recent entries. The two memories serve different needs: nearby detail and access to a much longer history.

Why compression is followed by selection

The collection of summaries still grows as the sequence grows. Reading every summary with every main attention head would leave another increasing cost. CSA therefore uses a Lightning Indexer to score compressed blocks for the current token and choose a limited set. Main attention then reads the chosen compressed entries together with the recent individual entries.

The compression reduces how many global entries are stored; the selection reduces how many of those entries main attention reads for a query. Selection still has its own scoring cost. Neither step makes the history free, and compression does not preserve independent access to every source token.

What should a token contribute to a compressed entry?

Start at the compressor in the CSA diagram. It needs to turn several token positions into one stored vector. Before deciding how to combine them, we need a vector from each position containing the features to be stored.

The compressor receives the same prepared inputs as the rest of this layer's attention module. For each token position, Day 2's input connection mixes that token's residual streams into one vector, then applies RMSNorm. Call this attention input h_t, where t is the token position. Earlier layers may already have used context to shape it.

These input features support all of the layer's attention work. The compressor has a narrower purpose: prepare content that can be combined into memory entries. A learned linear map lets training choose which combinations of the input features are supplied to that memory. Call the map W_C and its output a candidate content vector, c_t.

Collect these inputs across token positions in a matrix H: row 0 is h_0, row 1 is h_1, and so on. These rows belong to different token positions. Day 2's stream rows belonged to one token; its input mixture has already reduced them before we form H.

For one token, the content map gives

c_t=h_tW_C.

This is what “projected” means here: multiply the attention input by a learned matrix. Each output coordinate is a weighted sum of its input features. The map can also choose a different output width.

Take two prepared attention inputs for a small example, h_0=(1,0) and h_1=(0,1), and choose

H=\begin{bmatrix}1&0\\0&1\end{bmatrix},\qquad W_C=\begin{bmatrix}1&4\\5&2\end{bmatrix}.

The numbers are chosen so we can inspect the compressor without running the preceding layers. Multiplication gives

\begin{aligned}c_0&=(1,0)W_C=(1\cdot1+0\cdot5,\;1\cdot4+0\cdot2)=(1,4),\\c_1&=(0,1)W_C=(5,2).\end{aligned}

Thus (1,4) is the candidate content contributed by token position 0, and (5,2) comes from position 1. They have not been pooled yet. They are not the output of this layer's attention calculation.

For T token positions, input width d and candidate width c, the same map acts on every token:

H\in\mathbb R^{T\times d},\qquad W_C\in\mathbb R^{d\times c},\qquad C=HW_C\in\mathbb R^{T\times c}.

The map changes features within each token's vector. It still leaves one candidate per token. Compression will happen when several candidates are combined into one vector.

Our candidates are now ready to combine. They precede this branch's positional rotation: the released compressor first pools candidates, then applies RMSNorm and RoPE to the completed entry. We will return to why the entry needs scale and position information after building it.

How should the compressor combine those contributions?

A CSA entry must be built before the later queries that will use it. The compressor therefore learns a rule for retaining information from its group, rather than choosing a new mixture for every later query. An equal average is a natural first attempt.

For our candidate content vectors c_0=(1,4) and c_1=(5,2), the average is (3,3). Both coordinates give half their weight to each token. Giving one token more weight would change both coordinates together.

Can the rule instead favor token 1 in the first coordinate and token 0 in the second? Use (4,3.5) as a test of what the combining rule can express; these chosen numbers do not identify an optimal summary for language. Giving token 0 weight 1/4 and token 1 weight 3/4 yields

\tfrac14(1,4)+\tfrac34(5,2)=(4,2.5).

The first coordinate is right, but the second is too small. Exchanging the weights gives (2,3.5): now the second is right and the first is too small. The first coordinate requires token 0's weight to be 1/4, while the second requires it to be 3/4. One scalar weight for the whole vector cannot satisfy both.

Give each coordinate its own source shares instead. For coordinate 0, use shares (1/4,3/4) across the two tokens. For coordinate 1, use (3/4,1/4). This permits the two combinations we wanted.

Let the attention inputs determine the shares

A model needs to produce those shares from its inputs. A second learned map can give each token a score for every candidate coordinate. It reads the same attention input h_t as the content map. The input can therefore influence both what the token contributes and how strongly each coordinate contributes.

Call the score matrix Z. For our same two input rows, choose

W_Z=\begin{bmatrix}0&\log3\\\log3&0\end{bmatrix},\qquad Z=HW_Z=\begin{bmatrix}0&\log3\\\log3&0\end{bmatrix}.

The rows of Z belong to tokens 0 and 1. Its columns match the two candidate coordinates. These are scores, so they need not be positive or add to one.

As in Foundations' scores-to-weights calculation, exponentiate the scores and divide by a total. Here we want source shares separately for each coordinate, so the total runs down each column, across token positions:

\exp Z=\begin{bmatrix}1&3\\3&1\end{bmatrix}\quad\longrightarrow\quad S=\begin{bmatrix}1/4&3/4\\3/4&1/4\end{bmatrix}.

Each column total is four. Column 0 gives token 0 a quarter and token 1 three quarters; column 1 gives them the opposite shares. Multiply each candidate coordinate by its own share, then add across tokens.

\begin{aligned}\bar C_0&=\tfrac14\cdot1+\tfrac34\cdot5=4,\\\bar C_1&=\tfrac34\cdot4+\tfrac14\cdot2=3.5.\end{aligned}

Two token candidates have become one vector, \bar C=(4,3.5), using a different source mixture for each coordinate. That is the sequence compression in this example. The content and score matrices determine what survives; training must learn choices useful for later predictions.

Collect the pooling operation

For one group of m token positions, collect their width-c candidate content in C and their scores in Z, both of shape m\times c. Our example used m=2 and c=2.

Definition 3.1

Coordinatewise weighted pooling combines candidate content C\in\mathbb R^{m\times c} using scores Z\in\mathbb R^{m\times c}. For source position r=0,\ldots,m-1 within the group and coordinate a=0,\ldots,c-1, set

S_{r,a}=\frac{\exp(Z_{r,a})}{\sum_{u=0}^{m-1}\exp(Z_{u,a})},\qquad \bar C_a=\sum_{r=0}^{m-1}S_{r,a}C_{r,a}.

Each coordinate's source shares sum to one. The result \bar C has c coordinates.

The denominator's index u runs over the group's token positions. The sum reduces that token axis; it does not sum feature coordinates together. The entry no longer provides separate access to its m candidate vectors.

Let a candidate's place in the block matter

So far, exchanging two complete candidate-and-score pairs leaves the pooled result unchanged. The sum retains no record of which pair occupied the earlier slot. V4 allows a slot's position within the block to affect the shares by adding a learned offset to its scores.

Collect those offsets in P\in\mathbb R^{m\times c}, one row per block position and one column per candidate coordinate. The final scores are Z=HW_Z+P for the block. Our example used zero offsets; adding them changes the shares, while the pooling operation stays the same.

The pooled vector will be compared with queries and transmitted as a value. Its coordinate scale therefore affects the attention calculation. V4 applies RMSNorm to the completed vector to control that scale. The query also needs positional information about the part of the history the entry represents; V4 applies RoPE using the current block's start as its anchor. Day 5 works through that positional calculation. The order on this branch is candidate formation, pooling, normalization, then rotation and storage.

Give a summary access across a block boundary

We have a way to combine candidates, but still need to choose which positions can contribute to each entry. CSA emits one summary for every four new token positions. Start with the simplest grouping: positions 0–3 form one entry and positions 4–7 form the next.

Positions 3 and 4 might belong to the same identifier or expression, yet this grouping would never combine their candidate vectors in one entry. A later reader could consult both summaries; the compressor itself has had no opportunity to pool those two positions together.

CSA gives each summary candidates from its current four-token block and from the preceding four-token block. The entry emitted for block 4–7 can therefore combine candidates from positions 3 and 4. Source positions overlap between entries, while a new entry is still emitted only once per four new tokens.

Entry 0 has no preceding block. Missing positions should take no share of the pooled result. Padding their content with zeros alone would still let finite scores consume part of the denominator. Pad the missing content with zeros and mask its scores with negative infinity: their exponential amounts are then zero, excluding them from the shares.

Keep recent entries alongside these summaries

Return to the upper path in the opening CSA diagram. Even overlapping summaries merge several positions into each entry. A query resolving a nearby identifier or argument may need to distinguish those positions directly. The local branch supplies a separate stored vector for each recent position, using its own learned content map on the same attention inputs.

CSA keeps at most 128 individual recent entries alongside the compressed memory. “Local” refers to those individual entries; “global” refers to summaries extending across the history. After positions 0–7 arrive, both exist: eight local entries and two completed global summaries. Entry 1 includes candidates from all eight positions even while all eight also have local entries.

A token does not first leave the local window and then get compressed. Both branches are built from the same sequence of attention inputs. As more tokens arrive, the local store stays bounded while new summaries extend the retained history.

When may a query use a compressed entry?

Grouping positions creates a causal constraint. An individual entry depends on one token position; a compressed entry can depend on several. A query may use that entry only when every contributing position lies in its permitted prefix. Selecting it on the basis of a high indexer score cannot make an unfinished block safe to read.

After inputs for positions 0, 1 and 2 arrive, entry 0's fourth candidate is still missing. Position 3 can change both its candidate content and the score totals. We cannot treat the three-token result as the finished four-token summary.

Once position 3 arrives, all four candidates are available. Entry 0 can be formed, normalized and positionally prepared for the cache. The query at position 3 can use it when predicting token 4: the summary contains no input beyond that query's permitted prefix.

For block length m, number blocks from zero. Block j starts at token position jm and finishes at (j+1)m-1. A query at position t can read the finished summary when

(j+1)m-1\leq t,\qquad\text{equivalently}\qquad(j+1)m\leq t+1.

For m=4, entry 0 first becomes available at query 3 and entry 1 at query 7. The previous block has already arrived, so overlap does not move that boundary. These examples follow the pinned implementation's completed-entry boundary.

Suppose one call processes positions 0 through 5. Entry 0 is complete, but the next block has only positions 4 and 5. Keep their projected candidate content and scores as unfinished state. A following call adds position 6; position 7 finally completes entry 1.

The stored entry's rotary anchor is the current block's starting position. Entry 1 is anchored at token 4 and first available at query 7. Its anchor chooses a positional transform; completion chooses when it can be read. We will use both facts on Day 5.

Connect the calculation to the code

We can now name the arrays a pooling function receives. C contains candidate content already formed from the attention inputs. Z contains pooling scores, including any within-block offsets. Learned projections happen before this pooling core; the completed entry's normalization and positional transform happen after it.

For our example, pass candidates [(1,4),(5,2)], scores [(0,\log3),(\log3,0)], and group length two. With one batch axis added, the reference operation below returns [(4,3.5)].

The pooling core in Python

The input shape is B\times T\times c: batch size B, supplied token count T and candidate width c. The positive integer ratio gives group length m.

The integer part of T/m counts complete groups. Reshaping separates groups from positions within them. Softmax acts on those positions; matching multiplication and summation produce output shape B\times\lfloor T/m\rfloor\times c.

The streaming wrapper joins unfinished candidate content and scores to newly supplied ones, pools complete groups and retains the rest. Its grouping here is nonoverlapping; released CSA additionally maintains the two projection roles above.

We can now follow CSA's compressed-memory path from its input to a stored entry: prepare the attention inputs, project candidate content and scores, pool neighboring blocks, then normalize and position the completed summary. The recent-window path preserves individual entries alongside these summaries. Together they supply the two kinds of memory in the opening diagram.

CSA still has to decide which summaries a particular query will read. That is the indexer's job. Day 4 constructs its queries, scores and selected addresses; Day 5 combines the chosen summaries and recent individual entries in main attention.
