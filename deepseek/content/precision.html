Four bits need a scale

Sharing a cache removes copies; compression reduces its entries. Each retained entry still contains hundreds of numbers. V4.1 reduces the storage of those numbers too, using four-bit codes for global cache coordinates. Four bits offer only sixteen patterns, far too few to reproduce an arbitrary real value. A scale shared by a group of coordinates lets the same small codebook cover different magnitudes, at the cost of rounding.

For the first calculation, use the signed code magnitudes 0, .5, 1, 1.5, 2, 3, 4, 6. A stored scale multiplies every code in a group. We round each scaled coordinate to the nearest code, so the scale determines both the spacing and the largest value the group can retain.

Take values (.7,4) sharing one exact scale. At scale .5, nearest-code reconstruction gives (.75,3): the first value is close, but the second saturates at the largest available magnitude. At scale 1, reconstruction gives (.5,4). One scale must accommodate the group's range, so improving the representation of one value can worsen another. Grouping and scale encoding are therefore part of the numerical method as well as its storage cost.

“Floating point” divides the bits into roles. A sign bit chooses positive or negative; exponent bits choose a power-of-two scale; fraction bits refine a value within that scale. E2M1 uses one sign bit, two exponent bits and one fraction bit, totaling four. If the sign bit is b\in\{0,1\}, the exponent field is integer E\in\{1,2,3\}, and the fraction bit is m\in\{0,1\}, a normal finite value is q=(-1)^b2^{E-1}(1+m/2). The exponent-zero case instead gives magnitude m/2, allowing zero and .5. The sign bit applies to those values too.

The main V4.1 global cache uses E2M1 values with one eight-bit E4M3 scale per sixteen channels. E4M3 allocates one sign, four exponent and three fraction bits; this finite format can represent magnitudes through 448. Its scale can therefore lie on a finer grid than powers of two alone. The indexer uses groups of 32 and E8M0 scales: eight exponent bits and no fraction or sign bits, representing positive powers of two. In both cases the scale is stored, so it must itself be representable. A faithful quantizer must handle scale rounding, clipping values beyond the available range, midpoint rounding rules, layout and dtype conversion. A convenient list of real code values alone does not specify those choices.

Choose the stored scale before rounding values

The illustrative quantizer supplied its scale. The released kernel calculates and encodes one. Work with a finite group x\in\mathbb R^g, where g is the number of coordinates sharing a scale and i=0,\ldots,g-1 indexes them. Let A=\max_i|x_i|, its largest absolute value. Dividing that maximum by 6 would fit it to the largest E2M1 code magnitude, before accounting for rounding of the scale itself.

Write \operatorname{cast}_{E4M3} and \operatorname{cast}_{E2M1} for conversions to those formats, including their rounding. Let \operatorname{clip}(a,-6,6) keep a inside that interval, replacing an out-of-range value by its nearest endpoint. The scale is s, the stored low-precision coordinate is q_i, and \widehat x_i denotes its reconstructed value in the original units. The main global-cache groups have g=16 and use

s=\operatorname{cast}_{E4M3}\!\left(\frac{\max(A,6\cdot2^{-9})}{6}\right),\qquad q_i=\operatorname{cast}_{E2M1}\!\left(\operatorname{clip}(x_i/s,-6,6)\right),\qquad \widehat x_i=sq_i.

The maximum in the first expression puts a floor under the group's magnitude. After division by 6, that floor is 2^{-9}, the smallest positive E4M3 value, so even an all-zero group receives a nonzero scale. The scale is rounded to E4M3 before dividing the coordinates by it. Each scaled coordinate is then clipped, rounded to E2M1 and finally multiplied by the stored scale to reconstruct its value. Rounding a real-valued ideal scale only after computing q_i would follow a different path.

With a group maximum of 3, the scale is exactly .5. A coordinate 1.4 becomes 1.4/.5=2.8 in scaled units. The nearest E2M1 magnitude is 3, so reconstruction gives .5\cdot3=1.5. This is arithmetic on a supplied group, not an observation about trained cache errors.

Indexer Q/K instead use 32-coordinate groups and E8M0 power-of-two scales. The kernel selects the next power of two at or above the required scale. In its normal finite range, that is 2^{\lceil\log_2(\max(A,6\cdot2^{-126})/6)\rceil}. Here \log_2 gives the power-of-two exponent, and the ceiling rounds that exponent upward. For a group maximum of 3.1, the required scale is approximately .5167; the next permitted power of two is 1. E4M3 can instead represent a scale near .5167. Both formats use E2M1 coordinate values, but their scale grids and group lengths give different errors and storage costs. There is no second, tensor-wide scale in the V4.1 main-cache format.

What is packed, and what remains floating point?

The reconstruction gave us approximate coordinates. Saving space requires retaining their codes and scales, rather than keeping every reconstructed number in a full-width tensor. Follow one main-cache entry: its 512 coordinates occupy 256 code bytes, and its 32 groups need another 32 scale bytes.

Suppose a logical array has M rows of N coordinate values each, with N divisible by the scale-group size g. Packing means putting two four-bit codes into each eight-bit byte along a row. The code bytes therefore have physical shape M\times(N/2), while their scale array has shape M\times(N/g). Neither shape changes how many logical coordinates attention eventually reads: it must reconstruct N of them for every row.

The packed representation uses PyTorch's float4_e2m1fn_x2 dtype. A nibble is one four-bit half of a byte; the dtype's layout contract determines which code occupies each half. The quantizer delegates that byte layout to the framework. Serializing an independently invented low/high-nibble order would require checking that it matches this contract.

A main entry therefore has 256 value bytes and 32 scale bytes; an index key has 64 value bytes and four scale bytes. Scales are part of the entry's storage. The logical value width stays 512 or 128 when the packed byte width is halved.

The same function has an inplace=True path: it updates the existing array instead of returning a packed one. It casts to FP4 and reconstructs the floating values immediately, writing \widehat x back into the original numerical format. The minimal model chooses this path for its cache numerics and retains ordinary floating buffers. A packed serving cache must instead retain code bytes and scales, reconstructing entries as attention consumes them. Thus the first path can exhibit low-precision rounding error without occupying four bits per retained coordinate.

Precision also depends on the branch. V4.1 retains FP8 for local SWA KV, while the global main entries use the post-RoPE FP4 path above. Expert matrices use a further FP4 weight layout with groups of 32 and E8M0 scales; the reference's linear operation quantizes activations to FP8 before its mixed-precision matrix multiplication. An FP4 cache format does not imply that every attention multiply or every model tensor uses four-bit arithmetic.

Where 890 bytes per token comes from

We can finally combine two savings studied separately: fewer independently owned entries, and fewer bytes for each entry. Start by counting one entry of each kind. Then count how often each owner emits one.

The advertised cache slope should now be an accounting exercise rather than a mysterious model constant. One width-512 main entry uses 512\cdot4/8=256 value bytes. Its one-byte scales, one per sixteen coordinates, add 32. The width-128 index key uses 64 value bytes and four one-byte scales. Call these totals b_{main} and b_{index}:

b_{main}=512/2+512/16=288,\qquad b_{index}=128/2+128/32=68.

The cache owners at layers 2, 8 and 14 each generate one entry per two input tokens. Layer 20 generates one per token. Combining ownership density and entry formats gives

\left(\frac12+\frac12+\frac12+1\right)(288+68)=\boxed{890\text{ bytes/token}}.

This is the ideal packed global cache slope. It excludes local-window state, unfinished blocks, weights, temporary indices, allocator padding and workspace. For odd lengths, count completed entries with floor division. A million-token global cache in this ideal layout is 890 million bytes, about 0.829 GiB.

More explicitly, for sequence length T, the three ratio-two owners each have \lfloor T/2\rfloor complete entries and the ratio-one owner has T. Thus the ideal global payload is 356(3\lfloor T/2\rfloor+T) bytes. At even lengths this is exactly 890T; at odd lengths the incomplete groups have not yet entered the global cache. One GiB is 2^{30} bytes, which explains the conversion from 890 million bytes to approximately .829 GiB.

Our first CPU study reproduces this arithmetic from the pinned configuration. The minimal reference's floating-point, quantize/dequantize buffers do not physically allocate that packed layout. Measuring their size would answer a different question.

Quantization does not commute with every operation

A format specifies a coordinate grid. Rotating the vector changes which coordinates meet that grid. We therefore need the order of rotation and rounding, even when the unrounded rotation preserves all dot products.

An orthogonal rotation preserves a vector's norm, but quantization rounds its individual coordinates. For example, the vector (1,0) is exactly representable at scale one. A 45-degree rotation gives approximately (.707,.707), whose coordinates round to (.5,.5) in the chosen nearest-code example. Rotating the quantized original instead retains (.707,.707). The two orders produce different vectors despite the norm-preserving real-valued rotation.

V4.1 quantizes main cache entries after their rotary transformation. To study that choice, hold the vector and rotation fixed and compare both orders, reconstructing the outputs into a common coordinate frame. Report errors by vector and coordinate, not just a single favourable average.

Quantization-aware training exposes the model to the intended rounding pathway while its parameters are being learned. It can therefore adapt its representations to that numerical restriction. A post-hoc perturbation of random vectors cannot demonstrate that trained adaptation. It can still expose a format bug, a clipped value or a change in sparse selection when two scores are nearly tied.

V4 retains another precision boundary

Return briefly to V4. Its cache has the same purpose, but the stored coordinates and scale groups differ. Reuse the accounting method above with V4's own formats; the 890-byte result belongs to V4.1's owner schedule and cannot be carried across unchanged.

The byte count above belongs to V4.1. Applying it to V4 would mix two different designs: V4 uses other coordinate formats and keeps an independently compressed indexer path. To compare their storage, we have to return to the format of each branch rather than change a single bit-width in the V4.1 calculation.

The V4 latent also has width 512, with a 64-coordinate RoPE tail. Its main and local KV paths simulate FP8 on the first 448 coordinates while retaining the rotated tail in BF16. BF16 uses sixteen bits per value: one sign bit, eight exponent bits and seven fraction bits. It therefore costs two bytes per retained coordinate. The pinned Flash configuration uses power-of-two scales, one per group of 64 non-RoPE coordinates. An ideal packed entry under those choices contains 448+2\cdot64+448/64=583 bytes: FP8 content, BF16 rotary coordinates, then seven one-byte scales. The minimal implementation still retains reconstructed values in a floating buffer.

V4's indexer is a separate path. Its own compressor produces index keys; a normalized Hadamard transform is applied after RoPE before FP4 quantization, and its queries receive the corresponding transform. Applying the same orthogonal map to two real-valued vectors preserves their dot product. Quantization after that map can nevertheless change the numerical error because the values now meet the codebook along different coordinates. The V4.1 indexer source inspected here directly rotates and quantizes its Q/K without that Hadamard operation.

These choices explain why replacing every occurrence of “FP8” with “FP4” would fail to describe the version change. The RoPE-tail treatment, scale group, scale encoding, index-key source and cross-layer ownership all matter to the stored state. Each cache accounting must use the format of its own branch and model version.

Reconstructing a local window

There is one more way to retain less state: save the global entries when a prefix is evicted and rebuild recent local state when it returns. The temptation is to replay exactly one window of input tokens. The CED example showed the difficulty: a high-layer local row can depend on earlier tokens through the lower layers. Replaying one input window need not restore the same high-layer state.

Bounded replay reconstructs state from a shorter tail, accepting an approximation. It should be compared with a full reference on identical weights, tokens and positions. Compare hidden states, logits and, with a trained model, task outcomes. Approximate replay is not required to match exactly; its error and practical effect are what need measurement.

During replay, existing global prefix entries are reused rather than overwritten by reconstructed prefix states. The local state is what is being regenerated. New suffix state can nevertheless depend on the approximate reconstruction, so moving the cache-hit boundary can change later values. Replay needs its own write policy, not just another call to the ordinary append path.

The difficult cases are resumption boundaries and dependencies near the omitted history. A test that only resumes immediately after a fresh full prefill may miss those cases. Save the replay length, original positions and missing-state policy in each experiment record.
