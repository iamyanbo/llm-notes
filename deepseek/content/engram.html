A learned memory for a short token pattern

An attention cache remembers this request. Engram stores learned features with the model itself. If the same short token pattern appears in another request, its table can retrieve the same features again. The question is how to use that extra capacity without evaluating another large network at every token.

Begin with the embedding lookup we already use: a token ID selects one learned vector. That lookup sees only one token. Engram lets an ordered suffix—such as the current token and its predecessor—select several learned vectors. Each table has a fixed address rule, so lookup does not require comparing the current state against every stored row.

Here is a small address example. Choose token IDs (2,5), address rule 2u_{t-1}+u_t, and a table with seven rows. The rule gives 9; its remainder after division by 7 is 2. We therefore retrieve row 2. Another suffix can reach the same row: (1,0) gives 2 as well. Several tables with different address rules give a pattern several sets of features despite such collisions.

These are chosen integers to expose the lookup. The released module uses normalized token IDs, multiple hash heads and much larger tables; we derive those addresses later. First follow what happens to the retrieved features. A successful lookup alone cannot decide whether they belong in the current context.

Retrieved memory still needs context

Suppose two contexts end in the same short suffix. Engram retrieves the same learned features in both. The wider residual state can still distinguish a definition from a quotation of that definition. We want the retrieved value to contribute strongly in one context and weakly in another.

For a first calculation, hold that value at v=(2,-1). Let the context comparison be 1 in the first case and −1 in the second. The released gate's signed square root leaves these two numbers unchanged; sigmoid then gives approximately .7311 and .2689. The additions are (1.4621,-.7311) and (.5379,-.2689). We have changed the use of the memory without changing its address.

To compute that comparison, a learned projection turns the retrieved features into a key and a value. The key is compared with the contextual residual row; the value supplies the coordinates to add. We can now specify the two paths.

First use one residual row x_t\in\mathbb R^d, with d=5120. Concatenating retrieved vectors places their coordinates end to end in a row e_t\in\mathbb R^m, where m is their total width. Learned maps W_K,W_V\in\mathbb R^{m\times d} give two width-d rows: a key k_t for comparison with the context and a value v_t to add. A gate g(x_t,k_t) is a scalar between zero and one. The simplified update is

k_t=e_tW_K,\quad v_t=e_tW_V,\quad x_t^+=x_t+g(x_t,k_t)v_t.

The actual residual has four copies, indexed by a=0,1,2,3. Each row x_a\in\mathbb R^d gets its own projected key k_a\in\mathbb R^d; they share the value v. The comparison first controls the scale of the two rows. For coordinate i=0,\ldots,d-1, a learned gain \gamma_{a,i} is the product of the query-side and key-side gains. Let \epsilon=10^{-20} be the small positive denominator constant. Write R_{x,a} and R_{k,a} for the two rows' root-mean-square denominators, and z_a for their scaled comparison:

R_{x,a}=\sqrt{\frac1d\sum_{i=0}^{d-1}x_{a,i}^2+\epsilon},\qquad R_{k,a}=\sqrt{\frac1d\sum_{i=0}^{d-1}k_{a,i}^2+\epsilon},\qquad z_a=\frac{\sum_{i=0}^{d-1}x_{a,i}\gamma_{a,i}k_{a,i}}{\sqrt d\,R_{x,a}R_{k,a}}.

The mean squares run over the d features of one copy; \epsilon=10^{-20} keeps a zero row's denominator positive. A different statistic would result from averaging over all four copies together. Learned gains multiply the matching coordinate products in the numerator; they do not enter these denominators.

The scalar z_a can have either sign. The released gate takes the square root of its absolute magnitude, keeps its sign, and applies the sigmoid \sigma(s)=1/(1+e^{-s}). Square root compresses magnitudes above one and expands magnitudes between zero and one; it is a specific learned-path choice, not a consequence of normalized comparison. With the source's small magnitude floor,

g_a=\sigma\!\left(\operatorname{copysign}(1,z_a)\sqrt{\max(|z_a|,10^{-6})}\right),\qquad x_a^+=x_a+g_av.

The absolute value |z_a| removes the sign inside the square root. \operatorname{copysign}(1,z_a) returns a unit value with the original sign, including the floating-point signed-zero convention. The maximum supplies a floor before taking the root. The gate is therefore a scalar for one residual copy, while g_av is a width-d vector. This addition leaves the four-copy shape intact.

V4.1 places Engram at zero-based layers 1 and 14. It uses n-gram orders 2, 3 and 4, eight hash heads per order, and width 256 per retrieved head. The 24 vectors therefore concatenate to width 6,144 before projection. Key projections serve the residual copies, with a shared value contribution gated separately for each copy.

The retrieved rows become one residual update

One stream showed why the gate is needed. The actual block carries four streams, and each can need a different amount of the same memory. That requires four comparison keys but only one value. The shapes below follow from that choice.

At one token, the 24 addresses retrieve 24 vectors of width 256. Putting their coordinates end to end produces a row e\in\mathbb R^{6144}, since 24\cdot256=6144. We now need five width-5120 rows: four comparison keys and one shared value. Their combined width is 5\cdot5120=25600. With rows acting on matrices from the left, one learned map W_{KV}\in\mathbb R^{6144\times25600} computes all five, and the vertical bars below indicate concatenation along the feature axis:

[k_0\mid k_1\mid k_2\mid k_3\mid v]=eW_{KV}.

The four contextual residual rows x_a compare with their own keys. The gain \gamma_a in the earlier gate formula is the coordinatewise product of two learned width-5120 gain vectors. Both RMS denominators are calculated from the ungained vectors, separately for each copy, with the configured \epsilon=10^{-20}. The source accumulates the comparison and residual addition in FP32 before casting back to the residual dtype. At an exactly zero comparison, its copysign operation preserves the sign bit while applying the minimum magnitude under the square root; a programming language's usual sign(0)=0 would differ at that boundary.

The lookup itself also has a numerical path. Each flat table stores eight-bit floating values (E4M3 FP8), with one power-of-two scale (E8M0) per 32 coordinates. A retrieved width-256 row uses eight scales: reconstruct each group by multiplying its stored values by its scale, then return the row in the 16-bit BF16 format. The precision chapter explains the bit layouts. For following memory flow here, the essential point is that lookup retrieves both values and the scales needed to interpret them.

The layer tables have 384,006,168 and 384,016,682 rows respectively. In tensor-parallel execution, the table is divided across devices. Each device, called a rank in this code, owns a consecutive range of rows, contributes zeros for unowned addresses and participates in a sum across ranks. Exactly one owner supplies each requested row's real contribution. This describes the released lookup; fetching rows in advance from host memory belongs to the serving system.

Engram runs before its layer's attention/FFN block and its mHC coefficient prediction. The value addition can therefore change both subsequent sublayer computation and the residual-mixing coefficients. No extra convolution follows the lookup in this V4.1 path. We have reached the full conditional-memory operation: token normalization determines IDs, the suffix determines rows, a learned projection produces keys and a value, and the contextual residual determines four gates.

Which token identities reach the table?

We have followed the value into the residual state. Now return to the lookup address: which integers should represent the suffix? A table trained to treat two spellings alike must receive the same IDs at inference. This is why normalization belongs to the learned table's interface.

Our illustrative hash began with small integers. The released module must obtain its integers from an actual tokenizer. This matters because two token IDs can decode to spellings that the memory should treat alike. The lookup construction decodes each vocabulary entry separately, retaining special tokens. Unicode NFKC standardizes compatibility variants; NFD decomposes characters into base and combining components, after which the module can remove accents. Lowercasing and whitespace normalization then group further spellings. Leading and trailing whitespace is stripped, with a special provision preserving a token consisting of one space. Equal resulting keys receive the same compressed ID.

A token that is only part of a UTF-8 character needs a different rule. If decoding produces the replacement character, the implementation uses the tokenizer's raw token spelling as its key. If normalization would produce an empty string, it retains the decoded text instead. These choices determine addresses; changing them while keeping the learned table fixed would retrieve unrelated rows.

The original vocabulary contains V=129280 token IDs; the configured compressed vocabulary contains V_c=99092 IDs. Write the resulting map as c:\{0,\ldots,V-1\}\to\{0,\ldots,V_c-1\}. Construction assigns compressed IDs in tokenizer-ID traversal order and checks the resulting vocabulary size. Normalizing a whole sentence and tokenizing it again would be a different computation. The module maps each existing token ID through c.

A chunk boundary must preserve token history

Consider the same sentence processed in one call and in two calls. The early tokens of the second chunk still have preceding tokens from the first chunk. Resetting the n-gram history at that boundary changes their addresses even when attention caches are correct.

For maximum order four, preserve the relevant last three adjacent sequence positions and their boundary state. The source marks image positions with the sentinel -1, which means “stop this lookback,” rather than a token ID to hash. Do not skip across an image span to gather earlier text tokens. Missing positions use the compressed padding ID c(2), obtained by mapping the configured padding-token ID 2. Image positions themselves receive no Engram contribution.

The original Engram design also includes a short causal convolution, a learned combination across nearby positions that uses no future inputs. The V4.1 variant omits it. A reusable implementation should make the variant explicit, since copying that component from the original paper would add an operation absent from this model.

From a suffix to a flat table row

The seven-row example let us compute a lookup by hand. To reproduce the released tables, we must now replace its address rule while keeping the same sequence: combine an ordered suffix, take a bounded remainder, then select a learned row. The details below specify that replacement.

We can now replace the illustrative hash with the released construction. Fix an Engram layer l and a receiving position t. Let v_{t,j} be the compressed ID at lookback j: j=0 means the current token, j=1 its predecessor, and so on through three. Before the sequence begins, use the compressed padding ID. Encountering an image boundary also replaces that position and every more distant lookback with padding. Thus a suffix can include recent text after an image, but cannot continue through the image into earlier text.

The layer has four fixed odd integer multipliers m_{l,j}, one per lookback. They are drawn reproducibly using the integer seed 10007l for NumPy's number generator: the same layer and generator procedure produce the same multipliers. Their bound keeps each multiplication inside the signed 64-bit integer range. First multiply each compressed ID by its lookback's multiplier. Then combine those integer products by bitwise XOR.

XOR compares the binary digits at each place: its result is 1 when the two input bits differ and 0 when they agree. For example, decimal 15 has binary digits 01111 and decimal 10 has digits 01010. Their XOR is 00101, or decimal 5. The symbol \bigoplus means to repeat this operation over the indicated products. For order n\in\{2,3,4\}, denote the combined integer by b_{l,t,n}.

Each order has heads h=0,\ldots,7. Head h has prime size P_{l,n,h}: an integer greater than one divisible only by one and itself. Taking the remainder modulo that size gives a local address between zero and P_{l,n,h}-1. The release chooses distinct prime sizes for the heads; they share the XOR integer for a given order, but divide it by different moduli.

To store all these tables in one array, place their row ranges end to end. The offset o_{l,n,h} is the number of rows in all preceding ranges. Adding it converts the local remainder into an address in that flat array. The order is n-gram size two, then three, then four, with eight heads within each size. These 24 ranges are disjoint. Collisions can still occur between two suffixes inside the same head's range.

Collecting multiplication, XOR, remainder and offset in that order, the flat row address a_{l,t,n,h} is

b_{l,t,n}=\bigoplus_{j=0}^{n-1}m_{l,j}v_{t,j},\qquad a_{l,t,n,h}=o_{l,n,h}+(b_{l,t,n}\bmod P_{l,n,h}).

For a small worked instance of the same operations, choose multipliers (3,5,7) and lookback IDs (5,2,4). The order-two integer is 15\mathbin{\mathrm{XOR}}10=5. Extending to order three gives 5\mathbin{\mathrm{XOR}}28=25. With one illustrative head per order, sizes 7 and 11, and offsets 0 and 7, the addresses are 5 and 7+(25\bmod11)=10. The real table uses distinct primes beginning near sixteen million; the small numbers here expose the arithmetic.

In the last step, division gives 25=2\cdot11+3, so the local remainder is 3. The earlier seven-row range occupies flat rows 0 through 6; the next range begins at 7. Its local row 3 is therefore flat row 10. The offset changes where a head's row is stored, rather than changing the suffix hash.

Addressing and memory placement

The suffix address is known before the hidden state reaches Engram. That makes it possible to request the table rows early. Their contextual gates have to wait for the residual representation. This split is useful: lookup latency can potentially overlap earlier work, while the eventual contribution still depends on the current context. The address and the gate solve different parts of the problem.

A small table can demonstrate the computation. It cannot demonstrate the usefulness of 196B trained memory parameters. Larger tables also introduce a systems problem: storing or fetching rows may cost more than the arithmetic of applying them. Deterministic addresses permit prefetching, but an actual performance claim needs the memory placement and transfer schedule.
