More capacity without executing every parameter

In the transformer from Foundations, the feed-forward sublayer applies the same learned network at every token position. We can give that network a larger intermediate width, adding more learned features. Every token then passes through the larger matrix multiplications.

Suppose we want to store more transformations while limiting how much work each token uses. We can keep several feed-forward networks and choose a few for each input. Each network has its own weights and is called an expert. A router chooses which experts run; their output rows are then combined. This is a mixture of experts, or MoE.

We begin with the function computed by one expert. Once its output is known, we can build the mixture and the rule that chooses its members.

Inside an expert

Attention has already let the current token gather information from allowed positions. The feed-forward sublayer now processes the features carried at that position. An expert replaces a feed-forward network, so its input is one contextualized row. It does not perform another attention calculation. Two occurrences of the same token can still give it different inputs because their contexts differ.

What transformation should it apply? A linear map recombines the input features using fixed coefficients. Two linear maps in succession still form one linear map. A nonlinear operation between them lets the response change with the input.

A usual feed-forward unit applies an activation to one learned weighted sum. A gated unit goes further: it forms a feature from one weighted sum and controls that feature with another. Separate weights let the two branches respond to different combinations of the same input features. Multiplying their outputs makes the feature's contribution depend on both combinations. DeepSeek V4 uses the gated construction called SwiGLU.

Each projection box below contains a table of weights. Multiplying a row by that table forms new weighted sums of its features. We will call the gate table W_1, the feature table W_3, and the return table W_2. These names follow the three projections in the expert implementation.

Training adjusts the projection weights; a forward pass applies the resulting matrices to its input. The drawing uses chosen small matrices so that we can follow the calculation. Its row and column indices start at zero.

Read one column of the feature table

The blue input row is x=(1,2). Find the box labelled W_3: it has two rows, one for each input feature, and three columns, one for each feature it will produce. Its first column is (2,0). Multiply the first input by the first weight, the second input by the second weight, and add:

1\cdot2+2\cdot0=2.

The second column, (1,1), gives 1\cdot1+2\cdot1=3. The third, (0,1), gives 1\cdot0+2\cdot1=2. Collecting those three results is exactly what row-by-matrix multiplication means here:

xW_3=(2,3,2).

These are the three intermediate features on the right branch of the diagram. The multiplication used only the two numbers in this token's input row and the six stored numbers in W_3.

Use a second table to control those features

Now follow the same input row into W_1 on the left branch. Its columns are (1,0), (0,1) and (-1,1). They give 1, 2 and -1+2=1:

xW_1=(1,2,1).

These are the inputs to the gate activation, not yet the multipliers. For each scalar gate input s, SiLU computes

\operatorname{SiLU}(s)=s\,\sigma(s),\qquad \sigma(s)=\frac{1}{1+\exp(-s)}.

Here \sigma is the sigmoid. For a gate input of 1, SiLU gives 1/(1+e^{-1})\approx0.7311. For 2, it gives 2/(1+e^{-2})\approx1.7616. Applying it separately to the three gate inputs gives

\operatorname{SiLU}(xW_1)\approx(0.7311,1.7616,0.7311).

The feature row on the right has stayed (2,3,2) while this happens. The SiLU branch can amplify or reverse a feature as well as suppress it.

Match coordinates before adding anything

Multiply the first gate multiplier by the first feature, then do the same for the second and third. The symbol \odot means this coordinatewise multiplication. Call the resulting row p:

p=\operatorname{SiLU}(xW_1)\odot(xW_3)\approx(1.4621,5.2848,1.4621).

The first product is 0.7311\cdot2\approx1.4621; the second is 1.7616\cdot3\approx5.2848. The three products remain separate until the return projection combines them.

Read the return table

The row p now reaches W_2 at the bottom of the diagram. This table has three input rows and two output columns. Its first column is (1,0.5,1), so the first output combines all three products:

1.4621\cdot1+5.2848\cdot0.5+1.4621\cdot1\approx5.5666.

The second column is (-1,1,0). It gives -1.4621+5.2848+0\approx3.8227. The expert's output, written E(x), is therefore

E(x)=pW_2\approx(5.5666,3.8227).

The input and output both contain two numbers, but they contain different values. That matching width lets us add outputs from several experts, and later add the combined result to the residual state. Values displayed here are rounded; the diagram computes with unrounded numbers.

Write the same calculation for any width

We can now name the widths without changing the operation. Let d be the number of input and output features, and m_e the number of intermediate features inside an expert. Our example has d=2 and m_e=3. For an input row x\in\mathbb R^d, the projection shapes are

W_1,W_3\in\mathbb R^{d\times m_e},\qquad W_2\in\mathbb R^{m_e\times d}.

Both branches need the same intermediate width so their coordinates can be multiplied in pairs. That width can be larger or smaller than the input width. The basic expert function is the calculation we have just followed, collected into one expression:

E(x)=\left(\operatorname{SiLU}(xW_1)\odot(xW_3)\right)W_2,\qquad W_2\in\mathbb R^{m_e\times d}.

V4 Flash uses m_e=2048 and Pro uses 3072. Each expert has its own three parameter tables. The same tables are reused whenever that expert processes a token. We now have a complete function to choose and combine; first, we need to include V4's clipping operation at the point where it acts.

Bounding the intermediate product

In our calculation, the largest feature-branch value was 3. A trained projection can produce much larger values, and multiplying large values from both branches can enlarge the intermediate product further. DeepSeek V4 therefore clips the projection outputs before forming the product.

Look at the rows labelled xW_1 and xW_3 in the diagram. The gate-input row is capped above at 10. The feature row is clipped to the interval from −10 to 10. These are different rules:

Clipping acts on the projected values, before SiLU and the product
ProjectionIf its value is 20If its value is −20
Gate input, xW₁Use 10 as the SiLU inputKeep −20 as the SiLU input
Feature, xW₃Use 10 in the productUse −10 in the product

Our chosen values are inside these limits, so the worked output stays the same. For larger values, clipping changes the expert's function. The individual expert is now specified. We can give further copies their own weights and combine their outputs.

Combining routed and shared functions

Suppose two groups of tokens usually reach different experts, but both require some of the same computation. Each group of experts may have to learn its own copy. We could instead reserve part of the feed-forward capacity for computation that every token can use, leaving the remaining capacity available through routing.

This is the motivation for shared expert isolation in DeepSeekMoE. The shared expert runs for every token; the router chooses additional experts alongside it. The aim is to reduce duplication of common knowledge among routed experts.

Let the expert we calculated in §1.2 be the shared expert, written E_s. For the same input x=(1,2), we already have its output:

E_s(x)\approx(5.5666,3.8227).

We will keep this calculated row as the shared contribution. For the routed branch, use three chosen output rows so that the weighted addition is easy to follow:

Chosen routed outputs for x = (1, 2)
ExpertReturned row
E₀(2, 0)
E₁(0, 4)
E₂(−2, 2)

For this input, the router calculation in the next subsection selects experts 0 and 1, with final weights approximately 0.6600 and 0.8400. Their combined contribution is

0.6600(2,0)+0.8400(0,4)\approx(1.3201,3.3599).

Add this contribution to the shared expert's output:

\underbrace{(5.5666,3.8227)}_{E_s(x)}+\underbrace{(1.3201,3.3599)}_{\text{routed contribution}}\approx(6.8867,7.1825).

The same construction works with any selected set. Write \mathcal S(x) for the selected expert IDs and g_i(x) for expert i's weight. Then

y=E_s(x)+\sum_{i\in\mathcal S(x)}g_i(x)E_i(x).

V4 Flash selects six of 256 routed experts, while Pro selects six of 384. Both also run a shared expert. We have seen how their returned rows combine. The remaining question is how the input determines which routed experts contribute.

Choosing experts and weighting their outputs

We want the selected mixture to vary with the input. A learned projection can assign one score to each expert. For x=(1,2), choose the router matrix

R=\begin{pmatrix}1&0&-1\\0&1&0\end{pmatrix},\qquad xR=(1,2,-1).

Each column corresponds to an expert. The third score, for example, is 1(-1)+2(0)=-1. Follow a column through the calculation below.

V4 transforms these scores with square-root softplus. If a_i denotes expert i's resulting affinity,

a_i=\sqrt{\operatorname{softplus}(xR_i)},\qquad \operatorname{softplus}(s)=\log(1+e^s).

For our three scores, this gives a\approx(1.1460,1.4584,0.5597). Selecting the largest two keeps experts 0 and 1. We normalize their affinities over this selected set:

\frac{a_0}{a_0+a_1}\approx0.4400,\qquad \frac{a_1}{a_0+a_1}\approx0.5600.

V4 also applies a fixed routed scale \rho: 1.5 for Flash and 2.5 for Pro. Using Flash's value gives final weights g_0\approx0.6600 and g_1\approx0.8400, which are the weights used in §1.4. Expert 2 receives weight zero.

With N experts, the projection has N columns, so R\in\mathbb R^{d\times N}. Selecting K experts by their affinities and scaling the normalized weights gives

\mathcal S(x)=\operatorname{TopK}_i(a_i),\qquad g_i(x)=\rho\,\frac{a_i}{\sum_{j\in\mathcal S(x)}a_j}\quad(i\in\mathcal S(x)).

This is the selection rule before load balancing. The load-balancing correction in §1.7 will modify these selection scores. First, we examine V4's other way of choosing expert identities.

Choosing identities from the token ID

Tokenization turns the input text into a sequence of integer vocabulary IDs. Each ID selects a row from the embedding table—the lookup introduced in Foundations §2.2. Attention and the feed-forward layers then transform these embedding rows into contextual representations.

The original token ID remains available as those representations change. We can use it as a stable address for choosing experts: repeated occurrences of a token look up the same expert IDs, while their current hidden rows determine what those experts compute.

V4 uses this token-ID rule in its first three expert sublayers. A stored table maps each token ID to the routed expert IDs that should run. The released implementation calls this hash routing. For these layers, that table lookup replaces the Top-K choice of identities.

The selected experts still receive the current hidden row, and the router still computes affinities from it to weight their outputs. Repeated occurrences of the same token therefore choose the same expert identities in these layers, but can produce different weights and output vectors.

The later expert layers use the learned Top-K selection just developed. That selection creates another practical question: what happens when many tokens choose the same experts?

Distributing tokens among experts

Consider eight tokens, each selecting two of four experts. There are sixteen expert assignments in total. If each expert receives four assignments, the work is evenly distributed. If every token chooses experts 0 and 1, those two each receive eight assignments and the other experts receive none. The total count is still sixteen, but the busiest experts now have twice as much work.

During training, V4 adjusts per-expert selection corrections to influence this distribution. Write expert i's correction as b_i. For learned routing, the corrected selection rule becomes

\mathcal S(x)=\operatorname{TopK}_i(a_i+b_i).

For our router, the affinities are (1.1460,1.4584,0.5597). Initially, experts 0 and 1 are selected. Set expert 2's correction to 1.0. Its selection score becomes 0.5597+1.0=1.5597, so experts 1 and 2 now run.

In expert order 1 then 2, the original affinities are 1.4584 and 0.5597. Normalizing and applying Flash's scale gives g_1\approx1.0840 and g_2\approx0.4160. The routed contribution becomes

1.0840(0,4)+0.4160(-2,2)\approx(-0.8320,5.1680).

The shared expert continues to return the row calculated in §1.2. Adding it gives

y\approx(5.5666,3.8227)+(-0.8320,5.1680)\approx(4.7346,8.9906).

The number of executed experts has stayed the same, but the chosen functions and their combined result have changed. Move the correction below to see where that change occurs.

Change a selection correction and follow the chosen mixture.

Once the IDs are known, execution groups token rows by the expert they need. This is dispatch. Each expert processes its assigned rows, and gather returns the weighted results to the tokens they belong to. This groups the work by expert, then restores the original token order.

The implementation can multiply a selected expert's intermediate row by its scalar mixture weight before applying W_2. Because that return projection has no bias, linearity gives the same result as scaling the final expert output. Training decides how to update the selection corrections; the forward calculation here uses their stored values.

One representation can supervise another prediction

We have followed a token through an expert, combined expert outputs, and constructed the routing rules. These functions belong inside the main transformer. There is one more inherited training idea to locate before we finish Day 1: multi-token prediction, or MTP.

The main model learns to predict the next token. During training, the recorded continuation also tells us the token after that. An auxiliary module can use the main representation together with the recorded next token to make this additional prediction. This creates another supervised prediction task; it does not give the main next-token predictor access to the future token.

For the chosen sequence “the cat sat,” the main prediction after “the” targets “cat.” The auxiliary module also receives the recorded token “cat” and targets “sat.” The main prediction of “cat” must not receive “cat” as an input. The two tasks therefore have different input information and different targets.

Today we only need this purpose and information boundary. On Day 6, after constructing the other modules, we will connect the auxiliary module's inputs, transformer block and readout.
