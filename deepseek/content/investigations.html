Weighted pooling and cache accounting

The first experiment asks a small question with a definite answer. Does a four-token summary change if the tokens arrive in two calls instead of one? The streaming path has to carry the unfinished values and scores across the boundary. Comparing it with batch pooling tests that state handling directly, before a whole model can hide the error in its output.

The starting project isolates that weighted pooling core and the packed global-cache byte calculation. It does not load model weights or perform training. The recorded run uses Python 3.13.13 and PyTorch 2.12.0+cpu, with one CPU thread and seed 20261016. The seed fixes the synthetic inputs, allowing the same numerical cases to be repeated.

Precision and selection boundaries

The indexer makes a discrete choice from continuous scores. Suppose two candidate scores are 1.001 and 1.000 and only one can be retained. A rounding error of .002 can exchange their order even though both reconstructed scores are close to their originals. The same error cannot exchange scores 2 and 1. A precision study should therefore examine the gap at the selection boundary, not only an average score error.

Keep the query, keys, learned head weights and candidate set fixed. Compute higher-precision scores, then repeat after the chosen quantization operation. For Top-K, where K is the number selected, the boundary gap is the Kth greatest score minus the next greatest. Top-K overlap counts how many selected addresses both paths retain. These quantities connect reconstruction error to the discrete decision.

Vary magnitude, head count and deliberately constructed near-ties. A random average can hide the cases where a tiny perturbation changes a discrete choice. Conversely, a changed index need not produce a large output error if the two candidate values are similar.

Keeping the input tensors and weights fixed isolates precision as the changed variable. Saving raw scores, selected addresses and scale values would let us distinguish a large reconstruction error from a small perturbation near a selection boundary. With synthetic inputs, the conclusion concerns numerical sensitivity; learned retrieval quality would require trained representations.

Error after local-state reconstruction

Pause just before a prefix is resumed. One run has retained the full required state; the other has kept global memory and rebuilt local state from a short tail. Their first new prediction is where the missing history first becomes visible. Varying the replay length lets us ask how much reconstruction is enough for this fixed computation, before asking whether the change matters on a trained task.

For a fixed input sequence and parameters, pause both calculations at the same token position and compare the first resumed output separately from later outputs. If the first resumed logit row differs by .1 but the next 999 rows differ negligibly, averaging over all 1,000 rows can hide the boundary discrepancy. A per-position error plot makes that event visible.

Sweep depth, local window, prefix length and the location of a controlled dependency. Include an exact-replay reference if the small configuration makes that feasible. Approximate replay should be assessed by its error profile, not called a failed implementation merely because it differs from full state.

Here the changed variable is the reconstructed history, with the graph and parameters held fixed. State and logit errors by position, alongside replay work and memory, would show how the approximation behaves at resumption. Task success would require a trained model and an evaluation whose answer depends on the omitted history.

The cost of restricted indexing

A mask can change which candidates are selected without changing how many candidates were scored. With 1,000 global keys and a fixed allowed set of 100, dense-score-then-mask still computes 1,000 query–key comparisons before discarding 900 scores. Gather-before-score first retrieves the 100 allowed keys and computes only their comparisons. Both can implement the same selected-address rule, but their work and intermediate tensors differ.

First compare their raw allowed scores, selected addresses and final attention outputs on identical inputs, using a declared tie rule. Once they agree, vary context length while holding the allowed candidate count fixed. This separates an execution change from an architecture change that chooses a different candidate set.

Record the number of comparisons, intermediate tensor sizes and measured latency independently. A low comparison count can still run slowly because of gather overhead or poor hardware utilization. Include short contexts where the supposedly optimized path may lose.

Both paths must use the same visible entries and candidate rule, so the comparison concerns execution of one function. Preserving timing samples, workload dimensions and allocation measurements would show where a smaller comparison is offset by gathering or scheduling overhead. It would not establish the quality effect of training with a different selection budget.

Recording the next experiments

Before a run, write the question and expected outcome. After it, keep the raw result, the failed cases and the explanation that remains plausible. If a result changes after fixing a bug, preserve the correction rather than replacing it with a cleaner story.

The three investigations just outlined are proposals, not results. A useful record will keep the source revision, configuration, command and raw comparison, including cases that defeat the hoped-for saving. For this study, the interesting outcome is finding which assumption failed: that a small rounding error leaves a selection alone, that one replay window restores enough state, or that scoring fewer keys actually saves time.
