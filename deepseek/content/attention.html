The Lightning Indexer: compare a summary with the current token

The Lightning Indexer makes a cheap shortlist of compressed memories before main attention reads them.

Compression has reduced the history, but a long conversation can still leave thousands of compressed vectors. Reading all of them with main attention would still be expensive. So:

  1. Represent each compressed block with a small learned key. This is a compact description used for selection.
  2. Compare the current token's query with those keys. The indexer scores which blocks seem useful for what this token needs.
  3. Pass the highest-scoring block addresses to main attention. Main attention reads the corresponding richer compressed vectors, alongside recent individual token entries, and computes its own attention weights.

The indexer is a learned scoring module inside the attention layer, built mainly from projections and dot products. The indexer decides where to look; main attention decides what information to take from those places. Which blocks matter can change for every new token.

Consider the long source file from Day 3. A function call near its end may depend on a definition thousands of tokens earlier. Keeping the most recent summaries is a cheap selection rule, but can exclude that definition. Always choosing the same summaries has the same difficulty: the choice cannot respond to what the current token needs.

What is being compared?

Day 3's compressor learned what to put in a main-memory entry. Choosing whether to read that entry is another task. V4 gives the indexer its own compressor, with separate learned projections and a smaller output width. The two compressors describe the same source blocks at the same addresses, but can retain different features.

For a small example, take the following two-coordinate indexer keys. These are chosen, already prepared outputs of that separate compressor, not raw token rows or the pooled main-memory vector (4,3.5) from Day 3. We hold their position and precision transforms fixed while examining selection.

Among the completed entries, selecting the largest first key coordinate would always choose address 0. The keys alone cannot make the ranking change with the receiving token. We need a comparison that also uses that token's features. As in Foundations, a learned query supplies the receiving side of a query–key dot product.

Form the receiving side from the current input

The available input is the attention vector h_t from Day 3: the current layer's stream mixture after RMSNorm, before this layer's attention. For this one-token calculation call it x, and choose x=(3,4). Query projections will read this same row. They do not read an earlier stored summary.

A single query gives one comparison per key. Several learned query heads let the indexer make several comparisons before combining them. Main attention also needs its own queries. Mapping every input feature directly to all those query coordinates would require a large parameter matrix. V4 shares an intermediate query vector between the two modules, then gives each its own expansion. This intermediate is called the query latent.

We can follow that extra step without introducing all the heads at once. Choose the first map W_{Qa}=I_2, so xW_{Qa}=(3,4). Before expansion, V4 applies RMSNorm to control this intermediate's scale. With unit gains and epsilon omitted, the divisor is \sqrt{(3^2+4^2)/2}=\sqrt{12.5}, giving

z=(3,4)/\sqrt{12.5}\approx(.8485,1.1314).

This small illustration keeps the latent at width two so we can see its coordinates. In the released model it is narrower than the input. The saving comes with a restriction: later query maps can use only the distinctions retained by the latent. Normalization controls its scale; it does not recover a discarded distinction.

Use the latent to make two comparisons

We need each indexer query to have the same two-coordinate width as a key. V4 learns this expansion. For our example, choose four columns, enough for two such queries:

W_I=\begin{bmatrix}5\sqrt2/6&0&0&0\\0&0&0&5\sqrt2/8\end{bmatrix},\qquad zW_I=(1,0,0,1).

The first two output coordinates form query head 0, q_0=(1,0); the last two form head 1, q_1=(0,1). This arrangement changes no values. Both queries came from the same current input through the same latent, with different columns choosing their features.

Use them immediately on addresses 0 and 1. Head 0 gives scores 4 and 2, preferring address 0. Head 1 gives −1 and 2, preferring address 1. We have made the comparisons responsive to the input, but now two heads can disagree. An address needs one score for selection, so we must decide how those matches should combine.

Combine the head matches, then select completed addresses

For address 0 the pair of matches is (4,-1); for address 1 it is (2,2). Adding directly gives 3 and 4. Under that rule, the negative match in head 1 reduces the strong match in head 0. V4 chooses a different rule: each head contributes its positive match, while a negative match contributes zero before the heads are mixed.

Keeping the positive part is \operatorname{ReLU}(s)=\max(0,s). Our pairs become (4,0) and (2,2). This is a design choice, not a requirement of ranking. It changes which combinations of matches the indexer can distinguish.

Let the current input also choose the head mixture

Adding these positive matches equally gives 4 for both addresses. Equal addition has treated a strong match in one head exactly like two smaller matches. V4 lets the current input predict a coefficient for each head, so those contributions need not be treated equally.

The head-weight map reads the original attention input x=(3,4). Choose

W_w=\begin{bmatrix}2/3&1/3\\0&0\end{bmatrix},\qquad xW_w=(2,1).

These are two raw head coefficients. The implementation scales them by the reciprocal square root of head width times head count, controlling the numerical scale as those dimensions change. Here the divisor is \sqrt{2\cdot2}=2, leaving (1,1/2). This common positive scale does not change the ranking for a fixed query; it is V4's magnitude convention for the score.

Now head 0 contributes twice as much per unit match as head 1. The two addresses that tied under equal addition receive

I_{15,0}=1\cdot4+\tfrac12\cdot0=4,\qquad I_{15,1}=1\cdot2+\tfrac12\cdot2=3.

Addresses 2 and 3 similarly score 2 and .5. The final key would score 99. The following trace multiplies each rectified match by its head coefficient and adds across heads; it does not yet choose an address.

The coefficient map can predict different mixtures for a different input. Its coefficients are not constrained to be positive; our chosen pair is positive to make the arithmetic easy to follow. Rectification happens to the matches before this learned mixture, so final index scores need not be probabilities or even positive.

The largest score can still be unavailable

If we simply took the two largest scores, 99 would win. But that key uses positions 12–19, including inputs later than the receiving position 15. It remains unavailable regardless of its score. Apply the completion rule before ranking: exclude address 4, then keep the best two remaining scores.

Addresses 0 and 1 now win with scores 4 and 3. This two-address limit is chosen for the example. No softmax is needed: selecting the greatest scores requires their ordering, not normalized contributions to a vector sum.

We have followed the whole choice: the current token supplied queries and head coefficients; each key supplied comparison coordinates; rectification and the head mixture produced scores; completion determined which scores could compete. Main attention will read different, wider vectors at the selected addresses tomorrow.

To collect the score rule, let H_I be the number of indexer heads, q^I_{t,r} the receiving token's query in head r, k^I_j the stored key at address j, and w^I_{t,r} the scaled head coefficient just constructed. Then

I_{t,j}=\sum_{r=0}^{H_I-1}w^I_{t,r}\max\!\left(0,(q^I_{t,r})^\top k^I_j\right).

V4 uses 64 indexer heads of width 128 and a configured limit on selected completed addresses. Its scan is smaller than the many width-512 main-head comparisons. Selection still costs work over the indexer keys; the selected addresses limit the later main read.

Reference: how main attention uses the same query latent

The indexer needed only its own expansion to choose addresses. Main attention takes the same normalized latent z and uses a separate map. For a two-head example choose

W_{Qb}=\begin{bmatrix}1&0&1&1\\0&1&1&-1\end{bmatrix},\qquad zW_{Qb}=(z_0,z_1,z_0+z_1,z_0-z_1).

Arrange the first two coordinates as main head 0 and the last two as main head 1. Their raw pairs are approximately (.8485,1.1314) and (1.9799,-.2828). Larger query magnitudes can enlarge dot products without changing direction. V4 therefore also normalizes each main query by its own RMS, giving (.8485,1.1314) and (1.4,-.2). The indexer does not receive this additional per-main-head RMS operation.

For input width d, latent width r_q, main head count h and head width c, the two query matrices have shapes d\times r_q and r_q\times hc. Flash uses 4096\rightarrow1024\rightarrow64\times512. A direct map would contain 134,217,728 coefficients; the factored maps contain 37,748,736. Latent RMSNorm has learned coordinate gains; subsequent main-head RMS normalization has unit gains. The implementation uses epsilon 10^{-6}.

Shared-KV attention: read the entries at those addresses

Shared key-value attention is the main reader in V4. It gathers the selected compressed entries and recent individual entries, compares them with each main query, and combines their vectors. Today we construct that result, then follow how the stored vectors' position affects it.

The indexer has answered where to read. It has not yet chosen the coefficients in this vector sum. A block can be selected for all main heads while each head assigns it a different weight.

Reduce the stored side, keep several queries

A conventional multi-head construction can keep a separate key and value for every head at every retained position. That memory grows with both history length and head count. Sharing one key/value collection across heads removes the copies, while separate queries still permit different comparisons.

V4 makes a further restriction: the stored key and value are the same vector. A head compares its query with an entry, then transmits that very entry in the weighted sum. Training must learn coordinates that support both roles.

One head, two supplied entries

Use a separate small main-attention example. Take prepared query q=(\sqrt2,0), local entry c_0=(0,2) and global entry c_1=(\log3,10). These chosen vectors start at the comparison boundary, after their projections and positional preparation. They are not the smaller indexer keys used yesterday.

Use the scaled dot product from Foundations, dividing by the square root of this example's head width, \sqrt2. The two logits are 0 and \log3. Exponentiation gives amounts 1 and 3; dividing by their common total gives weights 1/4 and 3/4.

o=\tfrac14(0,2)+\tfrac34(\log3,10)=\left(\frac{3\log3}{4},8\right).

The first coordinate receives only the global entry's contribution; the second receives both \tfrac14\cdot2 and \tfrac34\cdot10. Each vector has supplied both its comparison coordinates and its transmitted coordinates.

Both entries competed in the same denominator. Normalizing the local and global branches separately would give each sole entry weight one, producing (\log3,12) instead. That is a different combination. V4 normalizes the gathered list once.

For the general head, let \mathcal A_t be that list's allowed entry IDs, c_j their stored vectors and q_{t,h} the query in main head h. Its logit for entry j is

\ell_{t,h,j}=q_{t,h}^{\top}c_j/\sqrt{512},\qquad j\in\mathcal A_t,

using V4's width 512. We have a vector sum. The next question is whether a head must always transmit a full unit of weight from real entries.

The attention sink: allow less contribution from real entries

Ordinary softmax assigns the real entries a total weight of one. Lowering every real logit by the same amount does not reduce that total: a common exponential factor cancels from numerator and denominator. A head can change which entry contributes, but cannot use this normalization alone to reduce the total real-entry weight.

V4 adds a learned attention sink: one logit per head with value zero. It competes for weight in the same denominator. Weight sent to this candidate contributes no vector to the output.

Keep the previous query and both entries fixed. Choose sink logit \log4, giving amount 4. The real amounts remain 1 and 3, so the common denominator becomes 8.

The local and global entries now receive weights 1/8 and 3/8. The sink takes the remaining half and transmits zero. Thus

o=\tfrac18(0,2)+\tfrac38(\log3,10)+\tfrac48(0,0)=\left(\frac{3\log3}{8},4\right).

Both output coordinates have halved. The relative proportion of the two real contributions is unchanged. The learned sink score lets the model adjust that extra competition; our value \log4 was chosen to expose its effect.

Let a_h be the sink logit in head h. Collecting the calculation gives

o_{t,h}=\frac{\sum_{j\in\mathcal A_t}\exp(\ell_{t,h,j})c_j}{\exp(a_h)+\sum_{j\in\mathcal A_t}\exp(\ell_{t,h,j})}.

The numerator is a vector. The sink adds to the scalar denominator and contributes zero to the numerator, so that denominator divides every output coordinate.
