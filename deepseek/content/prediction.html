Learning from more future targets

A full backbone has just processed “the” in a training example whose continuation is “the cat sat.” Its next-token head learns to predict “cat.” Could that expensive representation also help predict “sat”? During training, “cat” is already known, so an auxiliary module can receive its embedding alongside the backbone state and take on the second prediction. This is V4's multi-token prediction objective, or MTP.

Supplying the recorded next token to this auxiliary module is teacher forcing. It changes the information available to the second prediction, while the earlier backbone prediction still receives only the original prefix. We must keep those inputs separate when assigning their targets and losses.

Each prediction needs a score measuring agreement with its recorded answer. If the correct token receives probability p, use loss -\log p, with the natural logarithm. Increasing its probability from .25 to .5 reduces the loss from about 1.386 to .693. Summing such losses gives an ordinary next-token objective; auxiliary tasks use the same principle at shifted targets. This introduces the learning signal needed here, before the later chapter develops its gradients and optimizer.

Write the sequence as token IDs x_0,x_1,\ldots, and let t index the backbone position. The ordinary head predicts one step ahead, which we call depth k=1. A depth-k task predicts x_{t+k} after receiving the intervening teacher-forced tokens up to x_{t+k-1}. Denote its distribution by p_k and all learned parameters by \theta. Its negative log-likelihood penalizes assigning little probability to the recorded target:

\mathcal L_k=-\sum_t\log p_k(x_{t+k}\mid x_{\leq t+k-1};\theta),\qquad\mathcal L=\mathcal L_1+\sum_{k>1}\lambda_k\mathcal L_k.

Here \mathcal L_k sums over positions with a valid depth-k target; padding and document ends remove positions with no such target. The outer sum runs only over enabled auxiliary depths. Its nonnegative coefficients \lambda_k set their contributions to the combined loss \mathcal L. The conditional expression records which observed tokens a task may receive. It does not allow a head to read a future backbone row: that row has already processed the answer we are asking it to predict.

The fusion just constructed supplies the observed next-token embedding to the extra block while preserving four streams. Its output receives an auxiliary readout. We can now assign the ordinary and auxiliary losses without repeating that fusion: the ordinary head targets the next token; the extra block targets the token after that.

Apply the readout to the auxiliary block's own streams

After fusion, the auxiliary mHC block applies local attention and an expert update. It returns four rows, just as a backbone block does. To predict the further token, those rows need the same kind of learned reduction we used for the ordinary vocabulary head.

The auxiliary module has its own collapse predictor and final normalization. The computation is the one already worked in the three-ID readout example: predict four positive gains, take their weighted stream sum, normalize the resulting width-d row, then apply the vocabulary matrix. Use the auxiliary block's final streams in place of the backbone's streams.

V4 shares its embedding table and vocabulary matrix between the backbone and this auxiliary module. Fusion, the extra block, the reduction predictor and final normalization retain their own parameters. Both Flash and Pro use one auxiliary depth. Under our alignment, the ordinary head at position t targets x_{t+1}; the auxiliary branch targets x_{t+2} after receiving the recorded x_{t+1}.

DSpark drafting

At generation time, the actual next token is no longer available in advance. We could ask a cheaper model to guess several tokens and let the target check them. But making each guess with another heavy sequential pass would consume much of the saving. V4.1's DSpark does the heavy draft computation for several slots together, then uses a smaller recurrence to let each sampled token affect the next proposal.

V4.1's DSpark separates these two kinds of work. Three heavy draft blocks produce a base vocabulary-score vector at each of five slots. A small Markov component then adjusts each slot using the preceding sampled token. This retains a short sequential dependency without repeating the heavy blocks for every proposed token. DSpark is trained after backbone pretraining; it is a different branch from V4's backbone MTP objective.

The released configuration uses three draft blocks and five new draft positions. Its confidence outputs support a scheduler's estimate of how much of the draft will survive. Confidence is a prediction of acceptance, not permission to bypass verification.

First we can follow how the draft is constructed. We will then return to the probability rule needed to accept proposals while preserving the target distribution. The released minimal code supplies the draft forward path and raw confidence logits; target verification and scheduling require additional machinery.

The backbone features that seed a draft

The drafter needs a compact account of what the backbone has already found. Reusing features near the top of that computation avoids asking the draft blocks to reconstruct the entire history from token IDs. Three taps retain evidence from three depths; a learned map combines them.

A cheap drafter should receive useful evidence from the expensive computation already performed. In the pinned V4.1 forward, the evidence is taken immediately before backbone layers 37, 38 and 39 run. At each of these points, average the four residual copies rather than applying the vocabulary head's final learned or carried collapse. For a batch of B histories with S feature positions, each tap has shape B\times S\times5120.

Concatenation along the feature axis gives T\in\mathbb R^{B\times S\times15360}. With a row-map W_F\in\mathbb R^{15360\times5120}, the draft-history representation is

M=\operatorname{RMSNorm}(TW_F).

These are inputs to the selected backbone layers, not their outputs. The same projected history M is supplied to all three draft blocks. Each block has its own local-KV projection, so a shared history representation does not imply identical draft-block caches.

For one coordinate, suppose the three tapped stream means are .2, .7 and −.1. Concatenation retains all three as separate input coordinates to W_F; it does not average them into a single .267. The learned projection can therefore distinguish evidence from the three depths before normalization controls the resulting row's scale.

Let y_0 be the supplied known seed token. The draft input IDs are [y_0,\nu,\nu,\nu,\nu], where \nu=128799 is the configured noise token. The shared language embedding maps these IDs to B\times5\times5120, and repetition across four residual copies gives B\times5\times4\times5120. Initial input mixing selects copy zero. No sampled future tokens have yet entered these five rows.

Five rows through three draft blocks

We now have a shared history and five input slots: a known seed followed by noise placeholders. Process those slots together to obtain five expensive feature rows. The actual future token IDs are still undecided. Their sequential dependence will be added by the smaller head next.

Each draft block inherits the single-pass mHC attention/FFN structure. Its attention consumes the pre-mix carried from the previous sublayer; its newly predicted pre-mix is used by the FFN, which returns the next carried mix. Draft attention has no compressed global branch. It combines a window of projected backbone-history KV with the five temporary draft KV rows.

For nonzero start_pos, the reference expects one history-feature row, at original position p. Each draft block projects and RMS-normalizes it, applies RoPE, quantizes/dequantizes to FP8, and writes the corresponding history-ring slot. The five draft queries and KV rows receive positions p+1,\ldots,p+5. Every draft query can read all five temporary rows as well as the available history window. This visibility is deliberate: the unknown slots contain noise embeddings and their derived features, not teacher-forced future token IDs.

The queries use the inherited width-1280 latent, 64 heads of width 512 and score scale 1/\sqrt{512}. The same sparse-attention operation supplies the attention sink and shared latent K/V behavior. Afterward, the output's RoPE tail is inverse-rotated and the eight grouped output projections, each of intermediate width 1024, return width 5120. The block's MoE has one shared expert and 128 routed experts, selecting three routed experts for each draft row. Drafts use the text routing bias. SwiGLU clamping and residual mixing follow the block's usual operations.

At start_pos=0, the draft path instead projects the available history to seed its local caches and returns without evaluating the heavy draft blocks or sampling proposals. At a later one-row history update, the three blocks process the five rows jointly. Their temporary draft KV is concatenated for that call; it is not written into the long-lived history ring as five accepted tokens.

The inexpensive recurrence after the blocks

Hold the five heavy-block outputs fixed. Sampling a token should still change the distribution used for its successor. DSpark adds that dependence with a small token embedding and vocabulary bias, rather than another pass through the heavy blocks.

Use two vocabulary IDs and temperature one. A first slot with base logits (0,0) receives predecessor bias (\log3,0), giving probabilities (.75,.25). If ID 1 is sampled, let its embedding select bias (0,\log3) for the next slot. With the same zero base logits, the next probabilities are (.25,.75). This is one conditional path, not an assertion that ID 1 must be sampled.

The heavy blocks have processed all five slots together, before the five proposed tokens are known. The second proposal must still be able to depend on the first sampled token. Repeating the heavy blocks after each sample would give up that parallel work. A smaller recurrent head introduces the dependency after their output has been computed.

After the third block, collapse its four residual copies with the carried pre-mix. Call the resulting row at draft slot i u_i\in\mathbb R^{5120}, for i=0,\ldots,4. The final draft RMSNorm and shared language vocabulary projection produce base logits \ell_i\in\mathbb R^V, with V=129280. These five expensive base vectors are now fixed for this draft call.

The Markov component has its own embedding table E_M\in\mathbb R^{V\times256} and output matrix W_M\in\mathbb R^{256\times V}. A known or newly sampled predecessor y_i selects a width-256 row m_i=E_M[y_i]. Multiplying by W_M gives a vocabulary bias b_i\in\mathbb R^V; adding it to the slot's base logits gives adjusted logits \widetilde\ell_i. With positive sampling temperature \tau, softmax converts these scores into the next proposal's distribution:

b_i=m_iW_M,\qquad \widetilde\ell_i=\ell_i+b_i,\qquad y_{i+1}\sim\operatorname{softmax}(\widetilde\ell_i/\tau),\quad i=0,\ldots,4.

Here \tau>0 denotes the sampling temperature; the implementation floors a positive temperature at 10^{-5}, and uses argmax separately at temperature zero. The recurrent dependency is in five small embedding/readout steps, rather than five repeated passes through the three Transformer blocks. The returned token array contains six IDs: the supplied y_0 followed by five newly sampled proposals.

The confidence projection receives [u_i\mid m_i]\in\mathbb R^{5376}, using the collapsed row before the final draft RMSNorm, and returns one FP32 scalar logit. The minimal function returns that raw logit, not a calibrated acceptance probability. It also returns the Markov-adjusted logits before temperature scaling. Any verifier computing proposal probabilities must use the actual sampling transformation; applying softmax directly to returned logits assumes temperature one.

The bracket [u_i\mid m_i] means concatenation: 5,120 heavy-block features followed by 256 predecessor features. The confidence map can therefore consider both the slot's representation and the particular predecessor that produced its proposal distribution. A scalar score still needs a trained interpretation and any required probability calibration before it can supply the scheduler's acceptance estimate.

The reference samples positive-temperature categorical probabilities using independent exponential draws: if a_v is a token probability and E_v\sim\operatorname{Exp}(1), it chooses \operatorname*{argmax}_v a_v/E_v. This is a sampling implementation, not an additional learned head. IDs still require the tokenizer's decoding rule to become output text.

Why verification needs a probability rule

If we simply accept every token from a cheaper drafter, we sample from its distribution rather than the target model's distribution. With target p=(.5,.3,.2) and proposal q=(.2,.6,.2), the second token would occur twice as often as intended. Verification needs a rule that corrects this difference while retaining proposals when possible.

For one position and a fixed preceding history, let \mathcal V be the finite token vocabulary. Both p and q are nonnegative distributions on \mathcal V summing to one. Draw a proposed ID y from q. An actually drawn proposal has q(y)>0, so the following acceptance probability is defined:

\alpha(y)=\min\left(1,\frac{p(y)}{q(y)}\right),

The probability \alpha(y) is one when the target wants at least as much mass as the proposal supplies. Otherwise it retains the fraction p(y)/q(y). For an ID with positive proposal probability, multiplying the probability of proposing that ID x by its acceptance probability gives q(x)\alpha(x)=\min(p(x),q(x)). IDs with zero proposal probability are never proposed and contribute zero accepted mass. Accepted proposals therefore fill exactly the overlap of the distributions, even if their supports differ.

Write [u]_+=\max(u,0) for the positive part of a real number. After filling that overlap, token x still needs mass [p(x)-q(x)]_+. Let R=\sum_{z\in\mathcal V}[p(z)-q(z)]_+ be the total missing mass; z is the vocabulary summation index. When R>0, sample a rejected proposal's replacement from

r(x)=\frac{[p(x)-q(x)]_+}{\sum_z[p(z)-q(z)]_+}.

For these distributions, accepted proposal mass is (.2,.3,.2), totaling .7. The remaining target mass is (.3,0,0). Rejection occurs with probability .3, and its residual distribution assigns probability one to the first token. Adding both contributions gives (.5,.3,.2), exactly the target. The denominator in the residual formula is needed only when rejection has positive probability.

For the general rule, sum the accepted masses to obtain A=\sum_x\min(p(x),q(x)). Since p sums to one, R=1-A, exactly the rejection probability. The output mass at x is therefore \min(p(x),q(x))+Rr(x)=\min(p(x),q(x))+[p(x)-q(x)]_+=p(x). If R=0, every proposal is accepted and no replacement distribution is needed. This proves the one-position background sampler's claim; it does not specify DSpark's production verifier.

Verification commits a prefix, not a whole tentative call

Use a tentative workspace as a mental model. Write five proposals there, accept the first two, and reject the third. The committed sequence gains those two IDs and the replacement for the third. Every cache must describe that same new sequence; the discarded fourth and fifth proposals have no committed state.

Suppose a draft proposes five tokens and the third is rejected. The first two may become history; the last two must not. The probability calculation is sequential even when the target evaluates several draft positions together. With committed history h, proposal position i uses target distribution p_i(\cdot\mid h,y_1,\ldots,y_{i-1}) and the drafter's actual conditional distribution q_i. Apply the ratio rule until the first rejection, emit its residual replacement and discard the remaining draft. If all proposals survive, an ordinary speculative sampler can emit an additional target token. This is the background exact sampler, not a specification of DSpark's production verifier.

That probability rule has a state consequence. Target evaluations of unaccepted proposals are tentative. Only the accepted prefix and the emitted replacement or additional target token belong to the committed history. A serving implementation must make the corresponding KV cache lengths, compression partial groups, local-ring contents, Engram suffix history and next position agree. Reducing a length counter alone cannot restore an old ring slot that tentative evaluation has overwritten; the implementation needs restorable state or a separate tentative workspace.

Future draft calls also need backbone taps and draft-history KV for the history actually committed. The rejected suffix cannot become the seed for a later Markov step or survive in those caches. The five temporary noise-slot features are never themselves evidence that five tokens were accepted. The confidence scheduler decides how many proposals are worth checking under the current workload; target verification still decides what becomes history.

The supplied minimal backbone returns last-position logits by default and its nonzero-start cache path assumes one-token updates. Its draft forward therefore does not by itself supply a batched verifier with every required target conditional and rollback operation. Completing that engine requires an additional multi-position target path and explicit state management. Nothing in the calculations here claims that such an engine, optimized CED serving, or its throughput has been implemented locally.

Choosing a draft length

A five-token draft that almost always fails at its first token spends work on four unused slots. One that is usually accepted in full can save repeated target calls. The scheduler therefore needs an estimate of how much of a block will become committed history, as well as the cost of computing and checking it.

Suppose the draft length is k. Let a_i estimate the probability of accepting proposal i conditional on all earlier proposals having been accepted. The probability chain rule gives the first-j survival estimate

\Pr(\text{first }j\text{ survive})\approx\prod_{i=1}^{j}a_i.

This multiplication does not assume independent acceptances: the conditioning is included in each a_i. Let N count accepted draft tokens before the first rejection. Counting one for each surviving prefix gives N=\sum_{j=1}^k\mathbf1\{N\geq j\}, where an indicator is one when its event holds and zero otherwise. Taking expectations gives \mathbb E[N]=\sum_{j=1}^k\Pr(N\geq j). For estimates (.9,.8,.5), the survival probabilities are (.9,.72,.36) and sum to 1.98 accepted proposals. The emitted output can also include a replacement or an additional target token, so 1.98 is not the expected total output count.

Turning that estimate into throughput also requires the target engine's cost at the chosen verification length, batching and system load. A good scheduler uses measured cost curves; multiplying a mean acceptance rate by a block size is not a complete performance model.

Correctness tests must include rejection at the first position, full acceptance, cache rollback and the final emitted token. Distributional tests on a toy vocabulary can compare empirical frequencies with an exactly known target. Useful speed or acceptance claims need trained proposal and target models.
