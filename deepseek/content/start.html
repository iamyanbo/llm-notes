Prerequisites

These notes continue Foundations. They assume its construction of a causal transformer, including embeddings, attention, residual connections, vocabulary logits and the next-token objective.

  • Linear algebra: matrix multiplication, dot products and linear maps.
  • Calculus: gradients and the chain rule.
  • Probability: conditional distributions, softmax and expectation.
  • Implementation: tensor shapes and basic PyTorch operations for the code sections.

Transformers in Practice provides broader background on memory and conditional computation. The code here uses small, randomly initialized text models so that we can inspect every intermediate tensor on a CPU. The released architecture is the subject of the essay; the smaller implementation gives us something we can run and check.

What we are trying to make less expensive

Foundations gives us a causal transformer. Before changing it, consider three ways we might ask more of it: give it more learned capacity, carry a richer state through the stack, or let it use a longer history. Each is useful, and each can enlarge the computation.

A wider dense feed-forward layer adds parameters but makes every token execute larger matrix multiplications. A wider representation carries more coordinates but also widens the functions that process it. A longer attention history retains more entries and gives each new full-attention query more comparisons.

DeepSeek V4 addresses these costs in three ways. It stores many feed-forward networks but uses only a few for each token. It carries several residual streams while keeping each attention or feed-forward input narrow. For a long history, it keeps recent tokens in detail and compresses older tokens, then selects which compressed entries to read.

We begin with one expert: a feed-forward network applied to one token. Then we study how experts are chosen, how the residual streams carry their outputs, and how attention reads the history. Once we understand these parts, we can put them together into the complete architecture.

Day 4 · Lightning Indexer: from the current token to addresses

Stay with one choice of summaries throughout the calculation. Each step answers a difficulty in the preceding attempt, from a ranking that ignores the receiving token to head matches that disagree.

  1. Make the choice depend on the current token. Compare recency and a stored-only ranking with a query–key comparison. Locate the prepared attention input and the indexer's separate compressed keys.

  3. Work through that rule. Compare signed addition, equal positive-head addition and the learned head mixture. Derive the mixture coefficients when they are needed, then calculate the scores.
  4. Respect completion before ranking. Reject a high-scoring future entry, then keep the best available addresses. Main-attention query expansion is an optional reference after this calculation.

The model family

Reference model sizes; revisit after the modules

There are three configurations to keep apart. V4 Flash and V4 Pro share a design at different scales. V4.1 Flash changes the memory dependencies, adds image input, and introduces learned tables addressed by short token sequences. We will build V4 first, then ask what V4.1 changes. The rounded counts below give the scale of the actual models: B means a billion parameters and T a trillion. Prefill processes the supplied prompt; decode extends it.

The gap between stored and active parameters is deliberate. An expert layer can hold hundreds of alternative transformations while executing only a few for one token. The rest still need storage. Thus a 284 B model with 13 B active parameters is neither a dense 13 B model nor a computation through all 284 B coefficients. V4.1's backbone count also excludes its 196 B conditional-memory parameters and its image pathway. These distinctions will matter when we count the work.

Conventions used here

We retain the notation developed in Foundations. Token representations are rows: H\in\mathbb R^{B\times T\times d} has batch size B, sequence length T and hidden width d. A row-map W\in\mathbb R^{d\times c} produces HW with output width c; PyTorch stores the transposed weight in Linear(d,c).

Token and layer indices start at zero. The row at position t may read positions j\leq t and predicts token t+1, as in the causal decoder. Compression indices, cache owners and residual-copy axes will be defined when those constructions arise.
